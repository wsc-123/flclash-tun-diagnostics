# 脱敏案例：IDBWM 重建 Fake-IP 冲突路由

本文根据一次本地排查整理，**是经过脱敏的事件摘要，不是原始日志**。个人网关替换为文档示例地址 `192.0.2.1`，接口与进程使用代号，时间改为相对时间；保留具有诊断意义的 Fake-IP 地址段和程序名称。

## 现象与直接原因

Windows 上 FlClash 开启 TUN 后域名访问超时，显式本机代理却能收到 HTTP 响应。诊断中某个域名返回 Fake-IP `198.18.0.92`，同时存在下列路由关系：

```text
198.18.0.0/24  → 192.0.2.1 → 物理 Wi-Fi 接口  （冲突项）
198.18.0.0/30 → 直连       → TUN 接口         （正常项）
0.0.0.0/0     → 198.18.0.2 → TUN 接口
```

对 `.92` 的访问匹配到更具体的 `/24`，被导向物理网关；正常 `/30` 仅覆盖 `.0～.3`。固定真实 IP 的 HTTPS 对照收到响应，用户手动删除异常 `/24` 后恢复访问，支持该路由为直接故障点。不能因此声称所有 IP 流量都完全不通。

## 捕获到的时间线

| 相对开始时间 | 事件 | 执行进程 |
|---|---|---|
| T+0 秒 | TUN 关闭时，起始快照已有冲突 `/24`；1452 枚举既有路由 | 枚举上下文不用于归因 |
| 约 T+20 秒 | 创建 TUN `/30`、地址路由与默认路由 | FlClashCore（进程 A） |
| 约 T+37 秒 | 1146：删除物理接口上的冲突 `/24` | IDBWM（进程 B） |
| 约 T+39 秒 | 1145：重新创建同一前缀、网关、接口的路由 | IDBWM（同一进程 B） |
| 约 T+81 秒 | 停止采集，冲突 `/24` 仍存在 | — |
| 停止后 | 用户运行生成器，手动执行命令并反馈网络恢复 | 用户操作，未包含在该轮 ETW 内 |

原始 ETL 与 JSONL 交叉核对一致；删除、创建事件的 PID 均对应 IDBWM，开始和停止快照中的启动时间也一致。本轮共导出 48 条筛选事件：27 条枚举、14 条创建、7 条删除。原始 ETL 约 2.4 MB，保留了启动枚举及目标重建事件。

## 来源定位及尚未确定的部分

本机版本信息将 `IDBWM.exe` 关联到 Intel Connectivity Performance Suite（版本 `2.1022.831.5`）。服务 `IDBWM` 的显示名为 Intel Dynamic Bandwidth Management，包装程序配置指定执行 `IDBWM.exe`。

证据定位到了**本轮删除/重建操作的执行进程**。无法仅凭这些记录判断其内部触发规则、是否收到其他组件请求，或此前每一次故障是否都由同一程序造成。也不能把另一个 Intel 网络服务直接等同于 IDBWM。此次没有完成停用该组件后的长期对照，尚不能宣称永久修复。

关闭 TUN 未清除冲突项，后台又发生重建，解释了本轮重新开启 TUN 仍无网的表现。网络属于何种场所，不能由私有网关地址或旧脚本标签推断。

## 可复用的排查方法

1. 保存故障时的路由和 DNS，并比较 TUN 与显式代理。
2. 在路由变化前开始记录；只有既有路由快照不能查出创建者。
3. 找 1145/1146 的目标前缀、网关和接口，结合 PID 与进程启动时间。
4. 将手动删除操作与后台变化区分，保留原始资料供本地复核。
5. 发现明确组件后再做有针对性的临时停用对照；不要仅凭安装了某软件就归因。
